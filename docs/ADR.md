# アーキテクチャ意思決定記録 (ADR)

本プロジェクトにおける重要な技術選定および設計判断の記録。
各 ADR は Y-Statements 形式で記録する: 「**文脈**において、**懸念事項**に直面したため、**決定事項**を採用した。これにより**長所**が得られるが、**短所**を許容する。」

---

## ADR-001: 認証・認可の二重ガード (Security)

**ステータス:** 承認済み

**文脈:** GAS Webapp は `executeAs: USER_ACCESSING` で動作し、ブラウザ側の UI と GAS バックエンドの両方で権限チェックが必要。

**決定事項:** フロントエンドの表示制御（UI の非表示・無効化）とバックエンドの権限チェック（`requireAdmin_()`・`ensureCaseEditableByActor_()`）を両方実装する二重ガードを採用する。

**長所:** フロントのバイパスによる不正操作をバックエンドで完全に防御できる。
**短所:** 同じロジックを2箇所に保守する必要がある。

## ADR-002: React on GAS (Frontend Architecture)

**ステータス:** 置き換え済み — v1.13.0 で ADR-013（本番ビルド方式）へ。ブラウザ内 Babel は開発用の原本（`index.html`）でのみ使う

**文脈:** GAS の `HtmlService` では Node.js ビルドパイプラインが使えない。しかし React の SPA を実現したい。

**決定事項:** Babel standalone を CDN から読み込み、ブラウザ内で JSX をトランスパイルする。ビルドステップなしで React を動作させる。

**長所:** clasp によるデプロイのみで完結。CI/CD パイプライン不要。
**短所:** ブラウザ内トランスパイルによる初回読み込みの遅延。バンドルサイズ最適化不可。

## ADR-003: タイムスタンプによる主キー管理 (Data Modeling)

**ステータス:** 承認済み

**文脈:** Google フォームの回答タイムスタンプを一意識別子として使用する必要がある。

**決定事項:** フォームの送信タイムスタンプを案件の PK として使用する。手動追加案件は `manual_` + エポックミリ秒 で衝突を回避する。

**長所:** フォームの IMPORTRANGE 構造を変更せずに PKを取得できる。
**短所:** タイムスタンプの衝突リスク（実運用上は無視できる程度）。

## ADR-004: ライブラリバージョンの固定 (Dependency Management)

**ステータス:** 承認済み

**文脈:** `esm.sh` 等のCDNでバージョン指定が緩いと、依存解決の過程で React 19 等が読み込まれる。React のインスタンスが複数存在すると `Minified React error #31` が発生してアプリがクラッシュした。

**決定事項:** 全外部ライブラリのURLにバージョンを完全固定し、`?deps=react@18.2.0` で依存も明示する。

```
良い例: https://esm.sh/lucide-react@0.330.0?deps=react@18.2.0
悪い例: https://esm.sh/lucide-react
```

**長所:** 予期せぬ破壊的変更によるクラッシュを完全防止。
**短所:** ライブラリ更新時は手動でURL書き換えが必要。

## ADR-005: インライン編集UIパターン（Popover + Overlay）

**ステータス:** 承認済み — v1.9.0

**文脈:** 管理者がステータス・担当者・上限値を変更する際、ページ下部のフォームへスクロールする操作が煩雑だった。

**決定事項:** `fixed inset-0 z-40` の透明オーバーレイ + 相対配置のポップオーバーパターンを採用する。

- バッジをクリック → `inlineEditField` state でポップオーバーを制御
- オーバーレイクリックで閉じる
- `useEffect` + `keydown` リスナーで Escape キーによるクローズ
- 案件切替時は `useEffect([selectedCaseId])` で自動クリア

**長所:** モーダルより軽量。スクロール不要で直感的。
**短所:** `inlineEditField: null | 'status' | 'staff' | 'caseLimit' | 'annualLimit'` の state 管理が増加。

## ADR-006: 新着バッジの実装方式（ID差分方式 vs タイムスタンプ方式）

**ステータス:** 承認済み — v1.9.0

**文脈:** タブに「最後に閲覧した時点から新しい案件が追加・移動した場合」にバッジ表示する機能を実装するにあたり方式を検討した。

**選択肢:**
- **A. タイムスタンプ比較:** `case.timestamp > lastViewed` でカウント → ステータス変更による案件移動を検出不可
- **B. ケースIDセット差分:** そのタブに存在したIDセットを保存し現在との差分をカウント → ステータス変更も検出可能

**決定事項:** B. ケースIDセット差分方式を採用する。

**長所:** ステータス変更による案件移動も正確に検出できる。
**短所:** 初回ロード時（localStorage未設定）は全ケースが新着として表示される（期待された動作）。

## ADR-007: Webapp 設定 — USER_ACCESSING / DOMAIN の採用

**ステータス:** 承認済み — v1.11.x 以前（確認: 2026/05/10）

**文脈:** GAS Webapp の `executeAs` には `USER_DEPLOYING`（デプロイ者の権限で実行）と `USER_ACCESSING`（アクセス者の権限で実行）の2択がある。`access` には `ANYONE`（誰でもアクセス可）と `DOMAIN`（ドメイン限定）がある。

**決定事項:** `executeAs: USER_ACCESSING` / `access: DOMAIN` を採用する。

**長所:**
- `USER_ACCESSING` により `Session.getActiveUser()` が確実に実際のログインユーザーのメールを返す。認証の信頼性が高い。
- `DOMAIN` により tadakayo.jp ドメイン外からのアクセスを完全遮断できる。

**短所:**
- `access: DOMAIN` のため外部ユーザー（ドメイン外の tadakayo.jp 以外）はアクセス不可（このシステムでは意図した制限）。
- 時間主導トリガはトリガ作成者の権限で動作するため、Webアプリのアクセスユーザー本人として Gmail 送信する用途には使えない。この制約により予約送信は v1.12.1 で廃止した。

**注意:** 旧 HANDOVER.md には誤って `USER_DEPLOYING` / `ANYONE` と記載されていたが、実際の appsscript.json は `USER_ACCESSING` / `DOMAIN` であることを clasp pull で確認済み（2026/05/10）。

## ADR-008: メール下書きのスプレッドシート実装

**ステータス:** 承認済み — v1.11.0

**文脈:** メール送信前の下書きを保存する仕組みが必要になった。選択肢として「PropertiesService（GASのユーザー設定ストア）」と「スプレッドシートの専用シート」を検討した。

**選択肢:**
- **A. PropertiesService:** GAS の UserProperties を使用。1ユーザーあたり最大 50KB の制限あり。本文が長いと溢れる可能性。
- **B. スプレッドシート専用シート:** 「メール下書き」シートを追加。容量制限なし。管理者が直接確認・クリーンアップ可能。

**決定事項:** B. スプレッドシート専用シートを採用する。複合キー `CASE_ID + STAFF_EMAIL + MODE + THREAD_ID` で上書き保存し、1セッション1下書きを維持する。

**長所:** 容量制限なし。管理者がスプレッドシートで直接確認・クリーンアップ可能。既存の DB パターンと一貫している。
**短所:** スプレッドシートへの読み書きコストが発生する（他のシート操作と比較して誤差範囲）。

## ADR-009: 予約送信のキューアーキテクチャ（スプレッドシートキュー + 時間主導トリガ）

**ステータス:** 廃止 — v1.12.1

**文脈:** 指定日時にメールを自動送信する機能が必要になった。GAS の環境でどのようにキュー処理を実装するか検討した。

**選択肢:**
- **A. Cloud Tasks / Pub/Sub:** GCP のマネージドキューサービス。信頼性が高い。追加の GCP 設定・認証・費用が必要。
- **B. スプレッドシートキュー + 時間主導トリガ:** 予約をスプレッドシートに保存し、5分間隔のトリガで処理する。GAS のみで完結。
- **C. GAS の特定時刻トリガ:** 1件ごとにトリガを作成。GAS のトリガ上限（20個/プロジェクト）に抵触するリスク。

**決定事項:** B. スプレッドシートキュー + 5分間隔の時間主導トリガを採用する。`LockService.getScriptLock()` で並行実行を防止。`sending` 状態で 10 分以上経過した行はスタックとみなして再処理する。

**長所:** 追加の外部サービス不要。GAS のみで完結。スプレッドシートで予約状況を可視化・管理できる。
**短所:** 送信タイミングに最大5分の遅延が生じる。GAS の実行時間上限（6分）内で処理するため1回のトリガで最大 `SCHEDULED_BATCH_LIMIT=20` 件に制限。

**廃止理由（v1.12.1）:** 時間主導トリガはトリガ作成者のアカウントで実行される。`Gmail.Users.Messages.send(..., 'me')` の `me` が予約者本人ではなくトリガ作成者になるため、「Webアプリにアクセスしている本人のメールアドレスから送信する」要件を満たせない。予約送信 UI/API は撤去し、旧キューは `disablePendingScheduledEmails()` で `disabled` 化する。

## ADR-010: 管理機能ステータス遷移の統一ゲートキーパーパターン

**ステータス:** 承認済み — v1.11.6

**文脈:** v1.11.5 以前の管理機能（`setCaseStatusAdmin` / `reassignCaseAdmin` / `updateCaseDataAdmin`）は STATUS 列のみを直接書き換えていた。このため、`completed → inProgress` でHISTORY が保存されない、`→ unhandled` でスタッフ情報が残存するなど、11件の致命的・重大なデータ整合性バグが存在した。

**選択肢:**
- **A. 各関数に個別にロジックを追加**: 関数ごとに遷移ロジックを実装。重複コードが増加し、将来の漏れリスクが高い。
- **B. 統一ゲートキーパー関数**: `adminTransitionStatus_()` を1つ新設し、全ての STATUS 変更をここに集約。各関数はこれに委譲する。

**決定事項:** **B. 統一ゲートキーパーパターン**を採用する。

`adminTransitionStatus_(recordSheet, rowIndex, fromStatus, toStatus, actor, options)` が `fromStatus × toStatus` の全組み合わせを処理し、遷移に応じた DB 操作セット（HISTORY 保存・フィールドクリア・上限自動調整など）を確実に実行する。

**長所:**
- 遷移ロジックが1箇所に集約され、将来の修正・追加が容易。
- 全ての管理者経由 STATUS 変更が確実に整合性チェックを受ける。
- 関数の戻り値で変更後の全フィールドを返すため、フロントエンドの楽観的更新も正確になる。
- `completed → inProgress` で上限超過時に `caseLimitOverride` を自動調整するロジックも一元管理。

**短所:** 関数内の分岐が多く、将来の新ステータス追加時に分岐の追加が必要。

## ADR-011: FullCalendar 6.1.x をグローバルバンドルで埋込み

**ステータス:** 承認済み — v1.11.9

**文脈:** v1.11.7 までの日程確定モーダルは `<input type="datetime-local">` のみで、空き状況を視覚的に確認できなかった。タダスクや既存案件との重複を毎回手動で確認する運用負担があり、日程被りの事故リスクがあった。

**選択肢:**
- **A. importmap 経由で `@fullcalendar/core` 等を ES Module として読み込む**: 既存の React 用 importmap と同じパターン。ただし `?deps=react@18.2.0` 強制と独立した依存ツリーになりバージョン管理が複雑化。
- **B. `@fullcalendar/react` ラッパーを使う**: React ネイティブで宣言的だが、React 18.2.0 厳格固定（ADR-004）と相性が悪く、CDN 解決の工夫が必要。
- **C. グローバル UMD バンドル（`fullcalendar@6.1.18/index.global.min.js`）を `<script>` で読み込み**: core/daygrid/timegrid/interaction が同梱。既存の React コードと完全独立。

**決定事項:** **C. グローバルバンドル**を採用する。

`window.FullCalendar.Calendar` を `useRef` + `useEffect` でマウントするラッパーコンポーネント `ScheduleAvailabilityCalendar` を実装。

**長所:**
- React 18.2.0 固定制約と完全に独立して動作
- CDN キャッシュ後はバンドル取得コストが消滅
- 公式リファレンス実装と同じパターンで学習コスト最小
- バンドル内のプラグインバージョンが整合済みで、組合せ起因のバグ無し

**短所:**
- 初回読込みで ~200KB 増加（jsDelivr CDN 配信）
- 宣言的でない（命令的 imperative API を React の useEffect 内で扱う）

## ADR-012: 方法=Zoom 時のチームカレンダー強制登録 + 重複検知

**ステータス:** 承認済み — v1.11.8 / v1.11.9-r2 で確定

**文脈:** Zoom はタダスク業務とアカウントを共有しており、過去にダブルブッキングで会議が衝突した事故があった。一方、GoogleMeet / 電話 / 対面 / メール等は会議リソース競合の概念がなく、重複しても運用上問題ない。

**選択肢:**
- **A. すべての方法で重複チェック**: 一貫性は高いが、電話・対面で誤検知が出てユーザー摩擦が大きい。
- **B. Zoom + GoogleMeet+カレンダー登録 で重複チェック**: Phase 2 当初案。Meet も会議室扱いだが、複数 Meet 同時開催可能なので過剰。
- **C. 方法=Zoom 時のみ重複チェック**: Zoom リソース競合の防止に焦点化。他の方法はチェックなし。

**決定事項:** **C. Zoom 限定** を採用（v1.11.9-r2 で確定）。

加えて、Zoom 利用時は **`TEAM_CALENDAR_ID` への登録を必須化**する（`useCalendar` チェックの有無に関わらず）。これにより `getScheduleAvailability` がチームカレンダーを真実のソースとして重複検知できる。

**長所:**
- Zoom 衝突リスクが最重要なので、そこに集中投資
- 他の方法はユーザー操作を妨げない
- 個人カレンダー登録は引き続き選択制で柔軟性維持
- 監視対象は `TEAM_CALENDAR_ID` + `DISPLAY_CALENDARS_JSON` で運用可変

**短所:**
- 仕様変更：Zoom + useCalendar=OFF が「何もしない」→「チームのみ登録」に挙動変化（Manual.md / CHANGELOG で周知済み）
- `TEAM_CALENDAR_ID` にスタッフが書込権限を持つ前提（既存運用で満たされている）

## ADR-013: 本番ビルド方式（JSX 事前変換・React 同梱・Tailwind 事前生成）と起動の並列化

**ステータス:** 承認済み — v1.13.0（2026-11-25、利用者合意: フェーズC「ビルド方式」）

**文脈:** ADR-002 のブラウザ内 Babel は、毎回の起動で Babel（約3MB）の取得と約5,500行の JSX 変換を行い、React は esm.sh から多段で取得、Tailwind は開発用 CDN が実行時に CSS を生成していた。さらに `doGet` が全シートを読み終えてから HTML を返すため、サーバーのシート読込と画面資源の取得・変換が直列になっていた。ローカル実測（モックデータ・キャッシュなし初回表示の中央値）で 2,341ms・転送約5.1MB。

**選択肢:**
- **A. 変換結果をブラウザ（localStorage）にキャッシュ**: 手順は不変。初回・更新直後は遅いまま、Tailwind CDN は残る。万一 XSS があると改ざんされた変換結果が永続化するリスク。
- **B. 本番ビルド**: 原本 `index.html` から `npm run build` で `dist/` を生成し、clasp は `dist/` を push する。
- **C. 現状維持**

**決定事項:** **B. 本番ビルド** を採用する。
- 原本は単一ファイル `index.html` のまま（開発時はブラウザ内 Babel で即確認できる）。`src/` は作らない。
- `tools/build.js` が原本の目印（`build:dev-only`・`build:css`・`build:app`）に従い、esbuild で JSX を事前変換し React 18.2.0・lucide-react 0.330.0 を同梱（IIFE 1本・minify）、Tailwind v3 で使用クラスのみの CSS を生成して `dist/index.html` に埋め込む。`コード.js`・`appsscript.json` は複製する。
- React 18.2.0 固定（ADR-004）は `package.json` の版固定（`--save-exact`）で保証する。本番は CDN を使わないため React 19 混在の経路が構造的に消える。
- FullCalendar は日程確定モーダル専用のため、初期表示では読み込まず SRI 付きで遅延読込し、アイドル時に先読みする。
- `doGet` はシートを読まずに HTML を即返し（`createHtmlOutputFromFile`）、ページ先頭の素の script が `google.script.run.getInitialData()` を最初に発行する。シート読込と画面資源の読込・初期化が並行する。
- E2E は既定で `dist/` を検証する（出荷物を試験する）。デプロイは検査付きの `npm run deploy` に一本化する。
- **アプリ本体の JS は `<script type="text/plain" id="tadasapo-app">` に入れ、小さな起動用 script が間接 eval（`(0, eval)(…)`）で実行する。** 理由: GAS は配信時に、実行される種類のインライン script の中身を加工する（行が詰まる）。テンプレート文字列などを含む現代の JS が壊れ、`Uncaught SyntaxError: Invalid or unexpected token` で起動しなかった（2026-11-26 テストデプロイ @160〜@162。dist の 214 行目が配信後 127 行目になり、エラー位置は `"https://…"` の文字列の先頭。`//` 以降が切られたと推定）。v1.12 までは `text/babel` の中身を Babel が実行しており、GAS はその中身を加工していなかったため、同じ考え方に戻した。GAS の CSP は `'unsafe-eval'` を許可している。実行される種類のインライン script は「初期データの先行取得」と「起動用」の小さな2つだけとし、テンプレート文字列を含めない（単体テストで検査）。
- 予防策（調査の途中で疑った原因。どちらも単独では直らなかったが、配信側の加工に左右されないよう残す）: ① JS の `<script` を `\x3Cscript` に置き換え、`<script`・`</script` の形が残ればビルドを止める（GAS は `<script` に `nonce` を書き足すため）。② JS を ASCII だけで出力する（esbuild `charset: 'ascii'`）。JS・CSS に ASCII 以外、HTML 全体に BMP 外の文字（絵文字など U+10000 以上）が残ればビルドを止める。esbuild は正規表現リテラル内の文字をエスケープしないため、日本語を含む正規表現は原本で `new RegExp('…')` と書く。

**長所:**
- ローカル実測で初回表示 2,341ms → 629ms（-73%）、転送 約5.1MB → 約0.76MB（-85%）。E2E 全体の所要時間も 3.3分 → 2.2分
- 本番の実行時に外部 CDN（esm.sh・unpkg・Tailwind）へ依存しない（供給網リスクと可用性リスクの削減）。`eval` 相当の実行時変換も無くなる
- 版の混在（React 19）が構造的に起きない

**短所:**
- ビルド工程とデプロイ手順が増える（`.clasp.json` の `rootDir` を `dist` にする必要。誤って原本を push しても動作はするが遅い）
- 開発時（原本・ブラウザ内 Babel）と本番（ビルド）で実行形態が異なる。E2E を `dist/` で回すことで出荷物の正しさを担保し、原本は `E2E_TARGET=src` で検証できる
- Tailwind は原本のクラス名を静的走査するため、文字列連結でクラス名を動的に組み立てると本番で欠ける（現状該当なし。新規コードでも完全なクラス名を書く）

## ADR-014: 秘密情報と本番識別子はスクリプトプロパティ（秘密は書込専用）

**ステータス:** 承認済み — v1.13.0（2026-11-25、利用者合意: Zoom 3項目＋固定パスコード）

**文脈:** `executeAs: USER_ACCESSING` のため、タダサポDB（スプレッドシート）は組織内メンバーが編集者である必要がある（受容リスク）。そこに Zoom の Client Secret 等を「設定」シートで保持していたため、組織内の誰でも読めた。さらに設定変更時の監査ログ（同シート内）に変更前後の値が平文で残っていた。スプレッドシート ID はコードに直書きされ、公開リポジトリに載っていた。

**決定事項:**
- `SPREADSHEET_ID` と秘密情報（`ZOOM_ACCOUNT_ID`・`ZOOM_CLIENT_ID`・`ZOOM_CLIENT_SECRET`・`ZOOM_FIXED_URL`（`?pwd=` を含む）・`ZOOM_FIXED_PASS`）はスクリプトプロパティに保存する。スクリプトプロパティはスクリプトのコードからのみ読め、シートの編集者には見えない。
- 秘密情報は**書込専用**: 管理画面には値を返さず「保存済み／未設定／シートに残存」の状態だけ返す。入力は password 欄で、空欄は「変更なし」、削除は明示操作。監査ログには「(変更)」等だけを記録し値を残さない。
- 移行は管理画面の「秘密情報をプロパティへ移行」（`migrateSecretsToProperties`）で1回実行する。冪等。シートのセルを空にし、過去の監査ログに残った平文を `[REDACTED]` に置換する。移行前の本番を止めないよう、未移行の間はシートの旧値を読む後方互換を持つ。
- Zoom のアクセストークン（有効1時間）は ScriptCache に最長50分保持し、認証情報の差し替え時は破棄する。401 のときは1回だけ取り直す。
- 一度シートに置かれた秘密は既に露出していたとみなし、移行後に **Zoom の Client Secret を再発行（ローテーション）** する（運用手順 RUNBOOK §3）。

**長所:** 組織内の誰でも Zoom アカウントの API 認証情報を取得できる状態を解消。公開リポジトリから本番識別子が消える。Zoom API 呼び出しの往復が減る。
**短所:** スクリプトプロパティはシートより見えにくく、設定漏れに気付きにくい（`SPREADSHEET_ID` 未設定時は起動時に明示エラー、デプロイスクリプトで設定済みを確認）。GAS エディタの閲覧権限を持つ開発担当者は値を読める（GAS プロジェクトの共有を開発担当者に限定する基準で担保）。

## ADR-015: 初期データは「完成品（スナップショット）」を配る。作り直しは書込後・定期・手動、読み方は Sheets API 一括を段階導入

**ステータス:** 承認済み — v1.14.0（2026-11-27、利用者合意: 反映遅れ5分以内＋手動更新・保存先 CacheService のみ・定期作り直しは業務時間のみ）

**文脈:** v1.13.0 まで、画面を開くたびに `getInitialData` がシート9枚を全行読み、結合・集計していた。テスト用デプロイ実測（案件203件）で、温まった DB でも約9秒（DB を開く約1.2秒＋案件の読込約4.9秒）、冷えた DB では約18秒（DB を起こすだけで約11.8秒）。DB の温め（`keepWarm`・5分ごと）を入れたが効果が薄かった。原因は2つ。(1) 誰が開いても同じ結果になる結合・集計を、開くたびに一から作り直していること。(2) 冷えた DB を起こすコストが、読み方（SpreadsheetApp／Sheets API）に関係なく利用者の待ち時間に乗ること。

**決定事項:**
- **完成品を配る:** 案件一覧（`getAllCasesJoined_` の結果）・マスタ類（`getMasters_`）・自動CC・認証に使うタダメンマスタの行・設定値（秘密情報キーは除く）を1つの JSON（スナップショット）にまとめ、gzip して CacheService（ScriptCache・全利用者共通）に分割保存する。`getInitialData` は完成品が使えれば **DB を開かずに** 返す。認証・権限判定は従来どおりサーバー側で行う（完成品のタダメンマスタ行を使う）。
- **有効性は世代番号で判定:** スクリプトプロパティ `SNAPSHOT_GEN` に世代トークンを持つ。書込のたびに新しいトークンへ替える（読み→加算をしないのでロック不要）。完成品は作り始めの世代を持ち、保存直前に世代が変わっていたら保存しない。利用者は「完成品の世代＝現在の世代」かつ「作成から最大 `SNAPSHOT_MAX_AGE_MIN` 分（既定10分）以内」の完成品だけを使い、使えなければその場で作り直す。
- **作り直しのきっかけ:** ①アプリからの書込後（書込を行う公開関数はすべて `runWrite_` で包み、終了時に `SpreadsheetApp.flush()` → 世代を更新）、②時間主導トリガー `keepWarm`（5分ごと・業務時間のみ。既定 毎日8〜20時）、③画面の「最新に更新」ボタン（`getInitialData(true)`）、④完成品が無い・古い・世代違いのとき。IMPORTRANGE で入るフォーム申込とシートの直接編集は書込として検知できないため、②③で拾う（反映遅れは通常5分以内）。
- **利用者ごとのデータは分ける:** 下書きバッジ（`draftCaseIds`）は利用者ごとに違うため完成品に入れず、画面表示後に `getMyDraftCaseIds()` で取りに行く。
- **読み方（作り直し側）:** スクリプトプロパティ `SNAPSHOT_READ_MODE` が `sheetsApi` のとき、Sheets API `values:batchGet` で9枚を一括で読む（日時はシリアル値と書式付き文字列の2回を並列取得し、書式付きで文字列になったセルだけを日時と判定して `Date` に戻す。`getValues()` と同じ形の2次元配列に揃える）。既定は `spreadsheetApp`（従来どおり）。切替前に管理者が `diagnoseSheetsApiRead()` で全セルの一致（日時は時刻値まで）を確認する。Sheets API が失敗したら、その回は SpreadsheetApp で読み直す。
- 完成品の形を変えたら `SNAPSHOT_FORMAT_` を上げる（古い形の完成品を読まない）。

**長所:** 大半の起動が DB を開かずに済み（CacheService の読込のみ）、冷えた DB の約11秒も、温まった DB での約4〜5秒の読込も利用者の待ち時間から外れる。作り直しは主にトリガー（裏側）で行う。世代番号でアプリからの書込は次の起動に必ず反映される。Sheets API への切替は既定オフで、全セル一致の確認後に1行の設定で切り替え・戻しができる。
**短所:** フォーム申込・シートの直接編集は最大で数分（通常5分以内、上限は `SNAPSHOT_MAX_AGE_MIN`）遅れて出る（「最新に更新」で即時反映）。書込直後に最初に開いた人は作り直しを待つ。タダメンマスタをシートで直接無効化した場合、起動（閲覧）の拒否は最大数分遅れる（書込操作は従来どおり毎回シートで権限を確認する。アプリからの無効化は即時）。完成品は CacheService に個人情報を含む（スクリプトのコードからのみ読める・最長6時間で自動消去。利用者の端末には残さない）。書込を行う公開関数を追加するときは `runWrite_` で包む必要がある（単体テストが、公開関数を「書込」か「読むだけ」のどちらかに分類しているかを検査する）。

## ADR-016: バックエンドを役割別のファイルに分割し、手で実行する関数を「管理者メニュー」に集める

**ステータス:** 承認済み — v1.14.0（2026-11-28、利用者合意: 役割別に分割・廃止スタブは削除）

**文脈:** バックエンドは `コード.js` 1ファイル（約6,000行・トップレベル宣言約280個・公開関数66個）だった。GAS エディタの「実行」プルダウンには開いているファイルの関数が並ぶため、人が手で実行する約20個（トリガー設定・診断・初期構築・移行）を66個の中から探す必要があり、見つけづらかった。

**懸念事項:** GAS は全ファイルを同じグローバル空間で名前順に評価する。トップレベルの定数が別ファイルの値を参照すると読込順で壊れる。同じ名前を2つのファイルで宣言すると、後のファイルが黙って上書きする。分割の作業で処理の中身を変えてしまう危険もある。

**決定事項:**
- バックエンドを `gas/` に役割別の「2桁番号_名前.js」で置く: `00_管理者メニュー`・`01_定数と設定`（版数コメント・IDX）・`02_認証と共通`・`03_完成品`・`04_初期データ`・`05_案件操作`・`06_メール`・`07_日程と会議`・`08_記録`・`09_管理者操作`・`10_移行と案件キー`・`11_廃止機能`。`src/` は使わない（フロントエンド分割の失敗で廃止した名前のため）。フロントエンド `index.html` は1ファイルのまま。
- `00_管理者メニュー` には GAS エディタから手で実行する関数だけを、使う順（①定期処理 ②診断 ③初期構築 ④移行・修復 ⑤廃止機能の後始末）に置く。画面から `google.script.run` で呼ぶ関数とトリガー用の関数は置かない。
- トップレベルの `const`/`let` はリテラルだけで初期化する。宣言はファイル間で重複させない。
- 本番ビルド（`tools/build.js`）が `gas/*.js` を名前のまま `dist/` 直下へコピーし、clasp は従来どおり `dist/` を push する。`npm run check` は `gas/01_定数と設定.js` の版数と IDX を照合する。
- 分割は構文解析器でトップレベルの文を切り出して移すだけにし、分割前後で全宣言がコメント以外完全一致することを機械的に確認した（宣言274個。予約送信の廃止スタブ6個は利用者の合意で削除）。
- 単体テスト `tests/unit/backend-layout.test.js` が上の規則（ファイル名・重複なし・定数はリテラル・メニューの中身と漏れ）を検査する。`snapshot-flow.test.js` は GAS と同じくファイルごとに名前順で評価する。

**長所:** `00_管理者メニュー` を開けば、手で実行する関数だけが実行プルダウンに並ぶ。役割でファイルを選べるため、処理を探す・直す範囲が狭くなる。読込順への依存や名前の重複はテストで止まる。

**短所:** 初めて分割版を push すると、GAS プロジェクトの旧ファイル「コード」は削除され、役割別の12ファイルに置き換わる（`clasp push --force` はプロジェクトのファイル一式を置き換える）。GAS エディタで旧「コード」を開いていた人は開き直す必要がある。関数の行番号や `コード.js:行` を指す古い記録（CHANGELOG・HANDOVER の過去の追記）はそのまま残る。新しいファイルを足すときは番号と役割の一覧（`gas/01_定数と設定.js` 先頭・AI_RULES のファイル構成）も直す。
